# ADR-0005: コア機能自体をプラグイン API の上に実装する

- **日付**: 2026-08-18
- **状態**: 保留(2026-08-23 に「採用」から変更。Phase 4 で再検討)

## 背景

非機能要件として拡張性(ツール / パネル / インポータ / エクスポータをプラグインで追加可能)を掲げている。
だが拡張ポイントは、実際に外から使われるまで不足に気付けない。

## 選択肢

1. **コアは直接実装し、プラグイン API は後付けする** — 初期実装は速いが、
   API を切る段になってコアが前提にしている内部状態が漏れ、拡張点が形骸化する
2. **コア機能自身をプラグイン API 経由で書く(ドッグフーディング)** — 初期に遠回りするが、
   API の不足がコア実装の時点で露見する

## 決定

案 2 を採る。選択ツール・テキスト編集・インスペクタ等の標準機能も、
プラグイン API(`registerTool` / `registerPanel` / `registerCommand`)を使って実装する。

## 理由

API のドッグフーディングにより、拡張ポイントの不足を初期に検出できる。
「コアだけが使える裏口」が生まれると、外部プラグインは同じことができず拡張性の要件を満たせない。

## 影響

- コア API(Command / Plugin)は Phase 2 完了時点で凍結する。以降の変更は
  [../basic-design/11-extensibility.md](../basic-design/11-extensibility.md) の更新とセットで行う
- 拡張ポイントの一覧と将来拡張の受け皿は [../basic-design/11-extensibility.md](../basic-design/11-extensibility.md)

## 保留に落とした経緯(2026-08-23)

**この ADR は「採用」と書かれたまま、一度も効いていなかった。**
`src/plugins/` は存在せず、コア機能はすべて直接実装されている
([issues](../issues.md) #1)。「採用」のまま放置すると、
**読んだ人が「そう書いてあるからそうなっているはず」と信じる**のが一番の害なので、
実態に合わせて状態を「保留」に落とす。

実装が案 1(直接実装 + 後付け)に流れたのは、Phase 0–2 で作っていたものが
「拡張ポイントが何であるべきか」を決めるより先に必要だったため。
何をプラグインにできるかは、コア機能が一通り出揃ってからのほうが正確に決まる。

**ただし案 2 の懸念(「コアだけが使える裏口」が生まれる)は現実に効いている。**
その形跡は Phase 4 で API を切るときの出発点になるので、ここに残しておく。

| 現状 | 拡張性への含み |
|---|---|
| すべての編集が `EditCommand` を通る([ADR-0003](0003-all-edits-as-commands.md)) | **API の芯はできている。** 外部から編集させる口は Command で足りる |
| `editorEvents`([`src/core/events/bus.ts`](../../src/core/events/bus.ts))が購読の口になっている | 観測の口も既にある。イベント名の集合が「プラグインが見られるもの」の実質的な定義 |
| `useUiStore` / `useSelectionStore` を UI が直接読んでいる | **ここが裏口。** パネルを外から足すには、ストアに触らずに選択と状態を読む口が要る |
| ツール(選択・トリミング)はステージに直書き | `registerTool` に相当する受け皿が無い。ここが一番遠い |

再検討は [roadmap](../roadmap.md#phase4) の Phase 4。そのとき採るのが案 1 の追認になるのか、
案 2 に戻すのかを、この表を出発点に決め直す。
