# ADR-0006: Docs 駆動開発への移行とドキュメント運用ルールの裁定

- **日付**: 2026-08-21
- **状態**: 採用

## 背景

このリポジトリには既に厚い設計ドキュメントがあった
(`docs/basic-design.md` 856 行 12 章 / `DEVELOPMENT.md` 255 行 / `README.md`)。
一方で docs-init が前提とする骨格 — INDEX からの配線・機能単位の設計書・ADR・ドリフト検査 — が無く、
「どの章を読めば足りるか」が人間の記憶に依存し、機能単位の判断ログを残す場所も無かった。

移行にあたり、既存ルールと docs-init のルールが 5 点で衝突した。
さらに移送作業中、ドキュメントと実装のドリフトが 3 件見つかり、裁定 6〜8 として決着した。
ルール衝突の裁定は蒸し返しの温床なので、決定と理由をここに残す。

## 決定と理由

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| 1 | 設計ドキュメントの置き場所 | **`docs/` をそのまま使う**(`Docs/` にしない) | macOS のファイルシステムは case-insensitive で、`docs` と `Docs` は同一 inode になる。`Docs/` を作ると既存 `docs/` に混ざる。docs-init 側で不変なのは役割と骨格であってフォルダ名ではない |
| 2 | `docs/basic-design.md`(856 行)の扱い | **章ごとに分解して移送**し、原本は削除 | 12 章が docs-init の骨格とほぼ 1:1 で対応した。骨格だけ作って本文を据え置くと SSOT が二層になり doctor が機能しない |
| 3 | `DEVELOPMENT.md` の扱い | **`docs/rules/development.md` へ移送**し、ルートから削除 | 開発ルールも設計ドキュメント群の管轄。ルートに残すと INDEX から漏れた文書が生まれる |
| 4 | ドキュメントと実装のズレを見つけたときの挙動 | **必ずユーザーに報告し、裁定を仰ぐ**(docs-init 優先) | 旧 `DEVELOPMENT.md` §3 は「理由を添えて設計書のほうを更新する」としていたが、これだと**実装側のバグを設計書に追認してしまう**。どちらが正か(実装のバグか設計の変更か)は人間が決める |
| 5 | Phase 進捗の正の場所 | **`docs/roadmap.md`**。README の実装状況表は要約 + リンクに縮める | 旧 `DEVELOPMENT.md` §9 は「別のタスクファイルは作らない」として README と basic-design §12 の 2 箇所で管理していたが、これ自体が既に二重管理だった。正を 1 つに決める |
| 6 | コミットメッセージの規約 | **prefix を付けず、日本語 50 字以内の要約**にする(実態に合わせる) | 旧規約は `<type>: <要約>` を定めていたが、実際の履歴 10 件はすべて prefix 無しの日本語だった。`<type>:` は changelog 自動生成やフィルタリングのために価値がある慣習で、このリポジトリはどちらもやっていない。**消費者のいない規約は守られないまま残り、次に読む人を混乱させる** |
| 7 | データモデルの正の場所 | **`src/core/document/model.ts` が正**。[06-data-model](../basic-design/06-data-model.md) は概念レベルの補足 | 旧 §5.1 のモデル定義は実装と大きく乖離していた(実装にある `slideShell` / `framework` / `stageClasses` / `designWidth·Height` / `htmlAttrs` / `assets` が 1 つも無く、実装に無い `Slide.overriddenHead` を載せていた)。`model.ts` は各フィールドに「なぜそれが要るか」の doc コメントを持っており、生きているのはこちら |
| 8 | Rust 側の依存の記述 | **`Cargo.toml` の実態に合わせる**(`zip` / `tokio` / `notify` の記述を削除) | 旧 §2 はこの 3 つを主要 crate として挙げていたが、依存にもコードにも存在しなかった。`zip` は**同じ文書の §5.2 が「専用のプロジェクト形式(zip コンテナ)は持たない」と明示的に否定**しており、構想段階の記述が §2 に残っていたと判断できた |

## 影響

- 旧 `DEVELOPMENT.md` §3 の「設計書と違う実装をしたら設計書を直す」は**廃止**。
  裁定 4 に置き換わった([../rules/development.md](../rules/development.md) §3)
- 機能単位の設計書は `docs/features/<機能名>/` に置く。新機能に着手する前に AI が自律的に作る
- 移行は一度のイベントではない。今回 `features/` 化したのは 3 機能のみで、
  残りは [../INDEX.md](../INDEX.md) に「📋 未文書化」として登録した。次にそのコードを触るときに作る
- 移行完了の目安は「推測マーカー 0 + 未文書化機能 0」。`/docs-init doctor` が残数を報告する
- 裁定 7 により、モデルを変えたときは **`model.ts` の doc コメントと 06-data-model の両方**を直す。
  ズレたときはコードが勝つが、黙って乖離させない(裁定 4 のとおり報告する)

## 移行完了(2026-08-23)

**「推測マーカー 0 + 未文書化機能 0」に到達した。**

| 条件 | 到達した経緯 |
|---|---|
| 未文書化機能 0 | 残っていた 5 件(presentation / persistence / slide-management / fonts / asset-pipeline)を作成([issues](../issues.md) #4、#11) |
| 推測マーカー 0 | 最後の 1 件だった [01-overview](../basic-design/01-overview.md) の「想定ユーザー」を確定([issues](../issues.md) #6) |

**完了は「もう乖離しない」という意味ではない。** 移行のイベントが終わっただけで、
裁定 4(ズレは黙って直さず報告する)と §3 のドキュメント更新義務はこれまでどおり続く。

実際、この移行の総仕上げで**ドキュメント側が事実と違っていた例が 3 つ**出た。
どれもコードを読むだけでは分からず、**測って初めて分かった**もの。

| ズレていた記述 | 実際 |
|---|---|
| [issues](../issues.md) #2「⌘B は Command 履歴を通らない」 | セッションを閉じる時点で履歴に載り、Undo 1 回で戻せる |
| [ADR-0005](0005-core-features-on-plugin-api.md) の状態「採用」 | 一度も効いていなかった(「保留」へ) |
| 新設した設計書の「テストが無い」2 件 | `cargo test` を回したら実在した |

**「そう書いてある」は「そうなっている」ではない。** 推測マーカーが狙っていたのは
まさにこの取り違えで、マーカーが 0 になった後もこの点だけは変わらない。
