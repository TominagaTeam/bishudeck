# ADR-0008: 手で触ってもらうまでを最短にする（ドキュメント更新の単位をマージ単位に緩める）

- **日付**: 2026-08-24
- **状態**: 採用

## 背景

このアプリの最終的な合否は、**ユーザーが実際にアプリを起動して触った結果**で決まっている。
smoke も Vitest も「壊れていないこと」は言えるが、「右ペインのこのボタンが期待どおり気持ちよく効くか」は
人が触るまで分からない。決着済み 36 件のうち大半がインスペクタ・ステージの操作感の課題であることがそれを示している。

その前提で 1 件あたりのコストを測ったところ、ボトルネックは検証コマンドではなかった。

| 項目 | 実測 |
|---|---|
| `npm run typecheck` + `npm test` | 約 6.5 秒 |
| smoke 全体 | 分単位（`--only` で 1 シナリオなら約 17 秒） |
| 1 課題あたりの変更 | src 平均 約 295 行 / docs 平均 約 114 行 |
| ラウンドトリップ | 1 課題 = 1 ブランチ = 1 コミット = 1 マージ = **手動テスト 1 周** |

効いていたのは **1 課題ごとに固定費を丸ごと払っている構造**のほう。
INDEX と ADR を読む・設計書を書く・ユーザーがアプリを起動して該当箇所まで辿る、
どれも課題の大小にほとんど関係なく一定量かかる。
issues #35（上付きボタンを列に入れた）は src 35 行の変更に対して docs 46 行と手動テスト 1 周を払っている。

さらに、[ADR-0006](0006-docs-driven-migration.md) 由来の
「ドキュメントは実装と**同一コミット**」を素直に読むと、**手で触ってもらう前に設計書を全部書き切る**ことになる。
触った結果ボツになれば、その設計書も書き直しになる。

## 選択肢

1. **現状維持** — 1 課題ずつ、docs 込みで完結させてから渡す。手戻りの範囲は最小だが、固定費を毎回払う
2. **docs を後回しにする** — 実装だけ先に渡し、docs は気が向いたら書く。速いが [ADR-0006](0006-docs-driven-migration.md) が潰した「設計書が嘘になる」状態に戻る
3. **束ねる単位を変える** — 手で触ってもらう単位を課題 5 件程度に束ね、docs の更新義務を「同一コミット」から「**同一マージ単位**」に緩める

## 決定

**選択肢 3。** 次の 4 つをセットで運用する。

| # | 取り決め | 効果 |
|---|---|---|
| 1 | 関連する課題を**最大 5 件まとめて 1 ブランチ**で実装し、手動テストを 1 周にまとめる | 手動テストの回数が 1/5 |
| 2 | 実装コミットには**触る前に必要な docs だけ**（該当機能の `design.md`）を含め、`issues.md` / `roadmap.md` / `decisions.md` は**触ってもらった後にまとめて 1 コミット**、それからマージする | ボツになった実装の設計書を書く無駄が消える |
| 3 | コミットは**課題ごとに分けたまま**にする（束ねるのはブランチだけ） | 1 件だけ気に入らなければ `git revert` で剥がせる |
| 4 | 渡すときは **dev server を起動した状態**で、触る箇所と手順を添える | ユーザー側の起動待ちと「どこを触るんだっけ」が消える |

**「同一コミット」は「同一マージ単位」に緩める。マージ前に必ず閉じる。**

## 理由

- **設計書が嘘になる窓が開くのはマージ前だけ。** master に嘘が入らない以上、
  [ADR-0006](0006-docs-driven-migration.md) 裁定 4（ズレは黙って直さず報告する）が守ろうとしたものは失われない。
  守っているのは「master のドキュメントが実装と食い違わない」ことであって、
  「作業中の一時点でも食い違わない」ことではなかった
- **束ねる単位を大きくしても切り分けは失われない。** コミットを課題ごとに保つ限り、
  「5 件のうち 1 件だけ差し戻す」は revert 1 回で済む。束ねることの唯一の実害は
  「どれが原因か分からなくなる」ことで、それはコミット粒度で防げる
- **5 件という数字の根拠。** 決着済みの課題を見ると、同じ画面（右ペイン・ステージ）に属する課題が
  3〜6 件単位でまとまって出ている（#36〜#41 など）。同じ画面なら、ユーザーは 1 回開いたついでに全部見られる。
  画面をまたぐ課題を束ねても、結局その分だけ触る箇所が増えるので効果は薄い
- **選択肢 2 を採らない理由。** 「後で書く」は必ず忘れる。
  [rules/development](../rules/development.md) §1 が「手順 5 を飛ばして次の作業に移らない」と書いているのは
  そのため。緩めるのは**タイミングだけ**で、マージの条件からは外さない

## 影響

- [rules/development](../rules/development.md) §1 の作業フロー表を、ブランチ単位の表に組み替えた
- **マージの条件は変わらない。** `typecheck` / `test` / （Rust を触ったら）`cargo test` が通り、
  触った機能の設計書・`issues.md`・`roadmap.md` が実態に合っていること。順序だけが変わった
- smoke に `--only=<シナリオ>` を足した（[rules/development](../rules/development.md) §2）。
  全体は分単位かかるので「渡す前に自分で確かめる」が実質できなかった。
  1 シナリオなら約 17 秒で、渡す前の自己検証が現実的な選択肢になる。
  **部分実行のときは `N/N passed` に「全体は未検証」と併記される** — 通ったように見えて通っていない、を防ぐため。
  **2026-08-25 追記: smoke は廃止した（[ADR-0009](0009-drop-smoke-e2e.md)）。**
  渡す前の自己検証は `typecheck` / `test` までで、UI の確認は手で触る 1 周に一本化された
- 束ねた結果 1 件だけ差し戻す場合、**その課題の `issues.md` の行も戻す**（決着済みへ移す前に戻す）

## `--only` を入れて分かったこと（2026-08-24）

**シナリオは順番に走ることを前提に育っていた。** 部分実行を入れて初めて表面化した。

`runDirectManipulation` は `__hseSelected` を、`runWorkspaceAndText` は `__hseDoc` を、
**それぞれ前に走るシナリオが `globalThis` に置いた**ものとして使っていた。
全体を順に流す限り成立していたので、8 シナリオのうち 2 つが単独では起動もできない状態が見えていなかった。

どちらも DOM を読むだけの純粋なヘルパーだったので、`panelHelpers()`（全ドキュメントへ注入される共通ヘルパー）へ移した。
`__hseLastUid` のような**状態**は各シナリオが自分でセットしており、移す必要が無かった
（`runDirectManipulation` は「`runEditingFeatures` が触っていないスライド」をわざわざ選んでおり、
順序への配慮は既にあった。漏れていたのはヘルパーの置き場所だけ）。

**部分実行は、それ自体がテストスイートの隠れた結合を暴く道具でもある。**
「順番に走らせれば通る」は「それぞれが独立して正しい」ではなかった。
