# inspector — テスト

方針の正は [basic-design/08-test-policy.md](../../basic-design/08-test-policy.md)。ここは個別ケースだけ。

EARS の 3 型: `WHEN <イベント> THE SYSTEM SHALL <動作>` /
`IF <条件> THEN THE SYSTEM SHALL <動作>` / `WHILE <状態> THE SYSTEM SHALL <動作>`。

## テストケース

### 色の解釈

| # | 種別 | ケース(EARS 形式) | 状態 |
|---|---|---|---|
| 1 | unit | WHEN 背景が未設定 THE SYSTEM SHALL 「なし」として扱う | 実装済み |
| 2 | unit | WHEN 背景がゼロ alpha に解決される THE SYSTEM SHALL 「なし」として扱う | 実装済み |
| 3 | unit | WHEN 色見本に渡す THE SYSTEM SHALL computed の色を 16 進に直す | 実装済み |
| 3a | unit | WHEN パレットの色と今の色を比べる THE SYSTEM SHALL 書き方の違いを無視して同じ色と見る | 実装済み |
| 3b | unit | IF 今の色がまだ分からない THEN THE SYSTEM SHALL どのスウォッチも点けない | 実装済み |

実体は `src/features/inspectorColor.test.ts`。

### 当たる先の切り替え

| # | 種別 | ケース(EARS 形式) | 状態 |
|---|---|---|---|
| 7a | 手動 | IF セッションが開いていない THEN THE SYSTEM SHALL 文字色を選択要素へ書く | 手で確認 |
| 7b | 手動 | IF セッションが開いていない THEN THE SYSTEM SHALL 選んだフォントを選択要素へ書く | 手で確認 |
| 7c | 手動 | WHEN 太さを変える THE SYSTEM SHALL 選択要素へ書く | 手で確認 |
| 7d | 手動 | WHEN 行揃えを押す THE SYSTEM SHALL 選択要素へ書き、押した段が点灯する | 手で確認 |
| 7e | 手動 | WHEN 行揃えのあとに Undo する THE SYSTEM SHALL 1 手で元に戻す | 手で確認 |
| 7f | 手動 | WHEN 要素を選ぶ THE SYSTEM SHALL 太さの初期値をその要素の実際の太さにする | 手で確認 |

**確かめ方は「テキスト編集に入らずに要素を選び、各欄を触る」。** 見出しを 1 つ選んで、
文字色・フォント・太さ・行揃えを順に当て、そのつど要素へ書かれているかを見る。

**ケース 7f が一番重要。** デッキの見出しは元から太字なので、`bold` を数値に直せない実装だと
メニューは先頭の 300 を出す。そこで別の欄を触った瞬間、ユーザーが指定した覚えのない 300 が書かれて
見出しが細くなる。「当たったか」だけを見る 7c では捕まらない。

**ケース 7a〜7b は、削除した「テキスト」パネルの機能が残っていることの確認**でもある
([decisions.md](decisions.md) #19)。ここが落ちたら、統合が機能の削除になっている。

ケース 7 の並びは要素スコープしか見ていない。**範囲スコープ側は既存のケース 5 と
`richText.test.ts` が持っている**ので、同じことを二度書かない。

| 71 | 手動 | WHEN 降ろした宣言を Undo する THE SYSTEM SHALL 箱とリストを 1 手で戻す | 手で確認 |

単体は `src/core/editing/listOverrides.test.ts`、白リストとの照合(66)と
貼り付け(67)は `src/core/editing/format.test.ts`。**68〜72 は実際のカスケードが要る**ので
手で確認する(元の課題は [issues](../../issues.md) #31)。

**ケース 58 と 70 が抜けると、直したこと自体が負債になる。**
遮っていないデッキにも上書きを書けば見た目は合うので、**症状としては何も見えない** —
代わりに書き出した HTML にエディタ由来の宣言が増え続ける。
**画面ではなく書き出した HTML を見て確かめる。**
対照には文字色を使う: サンプルデッキは `ul` にサイズと行間だけを宣言していて
色には触れていないので、**同じ 1 つの箱で「遮られる宣言」と「遮られない宣言」を同時に見られる**。

**ケース 60 は上書きの数を決めている。** 遮っているのは `ul` で、`li` はそれを読んでいるだけ。
測る前に直す順(文書順に、遮られていたらその場で当ててから次を測る)にしないと、
**デッキのルール 1 本につき行数ぶんの上書き**が書き込まれる。

**単体は jsdom のカスケードを当てにしない。** 遮った状態は `<style>` ではなく
`ul` / `li` へのインライン宣言で作る — プローブが見ているのは computed の食い違いだけで、
遮りの出どころは問わないため。**実際の数値(26px → 60px)が出るかは手で見る**。

**ケース 50 と 51 は見方が肝。** マーカーの幅を勘定に入れず文字だけの中心を見ると、
**`inside` にしたぶんマーカー幅の半分だけ右にずれて見える**
(実測 17.5px。修正前の 15.59px と原因がまるで違うのに値が近い)。
`Range` の矩形は `::marker` を含まない(marker はノードではない)ため、
自動で測っていた頃は行を一度だけ左に寄せてマーカー幅を実測し、それを引いてから中心を比べていた。
**揃えるべきは「マーカーと文字の塊」**で、文字だけではない。

**ケース 52 は状況を作らないと成立しない。** サンプルデッキは `ul` に `text-align` を宣言していないので、
確かめるには `ul, ol, li { text-align: left; }` を宣言しているデッキを使うか、
そのルールを一時的に足してケースそのものを作る。

**ケース 45 が抜けると全デッキが壊れる。** 誰も触っていない要素の computed は `start` で、
これを `left` と読むと、箇条書きを 1 回押しただけで**触ってもいない行揃えの上書き**が
すべてのリストに書き込まれる。

**ケース 5 が一番重要。** `data-hse-text-tools` を器に付け忘れると、
押した瞬間にセッションが閉じて書式が当たらない。この 1 件がその罠を固定している。
浮遊版を廃止したあとも罠は**インスペクタ側にそのまま残る**ので、チェックはそちらへ移した。

**ケース 6 は撤去したものが戻らないためのガード。** 浮遊ツールバーは本文を覆うので廃止した
([issues](../../issues.md) #23)。

見出しは元から太字なので、`bold` は**解除**として当たる。
判定を `<b>` の有無にすると通らない — 見ているのは「書式が選択範囲に届いたか」であって、
どちらに転んだかではない。

### 文字サイズの即時反映

| # | 種別 | ケース(EARS 形式) | 状態 |
|---|---|---|---|
| 7q | 手動 | WHEN サイズ欄に数字を入れる THE SYSTEM SHALL 適用ボタン無しで選択要素へ当てる | 手で確認 |
| 7r | 手動 | WHEN 文字書式パネルを描く THE SYSTEM SHALL サイズ欄に適用ボタンを出さない | 手で確認 |
| 7s | 手動 | WHILE テキストを編集している THE SYSTEM SHALL サイズを打つたび選択範囲へ当てる | 手で確認 |
| 7t | 手動 | WHEN サイズを適用する THE SYSTEM SHALL フォーカスを数値欄に残す | 手で確認 |
| 7u | 手動 | WHEN 続けて桁を打つ THE SYSTEM SHALL 1 手の Undo で打つ前に戻す | 手で確認 |

**確かめ方は「サイズ欄に `2` `4` と 1 桁ずつ打つ」。** 打った桁がそのまま欄に残り、
文字が打鍵ごとに大きくなること。
**包み直しを避ける仕組みそのものは `richText.ts` のものなので、unit のケースは
[editing-engine/test.md](../editing-engine/test.md) #118〜#121 が持つ**(同じことを二度書かない)。

**ケース 7t が一番重要。** `execCommand` 経路は毎回 iframe にフォーカスを戻すので、
戻し忘れると**2 文字目が本文に打ち込まれる**。unit では見えない
(jsdom には奪い合う実フォーカスが無い)ので、ここは手で打ってみるしかない。

**7u が「1 手で戻る」を見るには、直前のフォント適用から 800ms 空ける必要がある**
(engine の併合窓)。空けないと直前の操作ごと畳まれ、何を戻したのかが言えなくなる。

### ペインの幅と開閉

| # | 種別 | ケース(EARS 形式) | 状態 |
|---|---|---|---|
| 14 | 手動 | WHEN 右の境界をドラッグする THE SYSTEM SHALL インスペクタの幅を追従させる | 手で確認 |
| 15 | 手動 | WHEN インスペクタを広げる THE SYSTEM SHALL その分だけキャンバスを狭くする | 手で確認 |
| 16 | 手動 | IF 上限・下限を越えてドラッグする THEN THE SYSTEM SHALL 520px / 240px で止める | 手で確認 |
| 17 | 手動 | WHEN シェブロンを押す THE SYSTEM SHALL インスペクタの幅を 0 にする | 手で確認 |
| 18 | 手動 | WHILE 隠れている THE SYSTEM SHALL シェブロンを窓の内側に見せ続ける | 手で確認 |
| 19 | 手動 | WHEN もう一度押す THE SYSTEM SHALL 隠す前の幅で戻す | 手で確認 |

**左の境界でも同じことを確かめる。** 左右で同じ仕組みを使っているので、片方だけ見ると
もう片方の取り違えを見逃す。

**ケース 17 が一番重要。** グリッドのトラック幅を 0 にしても、border-box は自分の
padding + border より細くならないので `.inspector` に 25px の帯が残る。
**目ではなく実際の幅を測る** — 見た目では「だいたい消えている」で納得してしまう。

**ケース 18 は窓の右端が絡む。** 左ペインなら「窓の左端より内側にあるか」で足りるが、
右は**シェブロンの右端が窓幅を越えていないか**を見ないと、
はみ出した半分が見えていない状態を捕まえられない。

**開閉状態と幅は `localStorage` に残るので、確認は前回の続きから始まる。**
畳んだまま終わった次の回は畳んだ状態で立ち上がるので、
**確かめる前に「畳んでいたら開く」で状態を揃える**。

### 表示ロジック

**React コンポーネントの単体テストは `createElement` で書く**([decisions.md](decisions.md) #36)。
`vite.config.ts` の `include` は `src/**/*.test.ts` のみで `.test.tsx` は対象外だが、
JSX を使わなければ `.test.ts` のまま実体をマウントできる。
`inspectorField.test.ts` がその形で、**markup そのもの**(どのタグが行を包むか)を見ている。

**それでも、テストしたい判断は純関数として `.ts` 側に置くのが既定。**
`isTransparent` / `toHex` がその形になっているのはこのため。
**パネルの並びと既定の開閉を `inspectorLayout.ts` に切り出したのも同じ理由による** —
コンポーネントの中に書くと、意図を 1 行で言えるテストが書けなくなる。
`createElement` に降りるのは、**純関数に切り出せる判断が無いとき**(行のタグはその例)。
