# 既知の課題

「今マズいと分かっているが、まだ直していない」ものの一覧。技術的負債・妥協・積み残しを**全体で**把握するための場所。

**判定軸は「もう起きているか」。**
起きている → ここ。起きうるが**まだ起きていない** → [roadmap](roadmap.md) の「主要リスクと対応方針」。
やると決めていない案 → [ideas](ideas.md)。やると決まった作業は各機能の `design.md` の実装タスクへ。
この住み分けの根拠は [ADR-0007](adr/0007-issues-md-and-task-file-rule.md) と
[rules/development](rules/development.md) §9。

状態: `未対応` / `対応中 → features/<機能名>` / `解決` / `許容`

## 運用

- 実装中の妥協・後回しにした判断、気づいた不具合や負債は、その場で AI がここに書き留める（黙って流さない）
- **直すと決めた** → 対応する機能の design.md の実装タスクへ移し、状態を `対応中 → features/<機能名>` に
- **直した** → 状態を `解決` に（行は消さない。同じ轍を踏まないため）
- **直さないと決めた** → 状態を `許容` にし、理由をメモに残す（意図的な妥協と、忘れられた負債を区別する）
- 深刻度は 高（今すぐ困る） / 中（いずれ困る） / 低（気になる程度）の3段階

### 書き方

一覧表と本文の 2 層に分ける（1 件の説明が長くなり、1 枚の表では読めなくなったため）。
**一覧表がメタ情報の正**（# / 要約 / 影響範囲 / 深刻度 / 記入日 / 状態）、
**詳細セクションが説明の正**。同じ事実を両方に書かない。

- 新しい課題は**両方**に足す — 「未解決」の表に 1 行、`## 詳細（未解決）` の末尾にセクション 1 つ
- 詳細セクションはメタ情報を繰り返さず、`**症状**` / `**原因**` / `**次の一手**` の太字ラベルで区切る
- 状態が `解決` / `許容` になったら、表の行と詳細セクションを**決着済み側へ移す**（消さない）。
  本文は `**何が起きていたか**` / `**どう決着したか**` に組み替える
- アンカーは見出し直前の `<a id="iN"></a>`（課題番号だけの安定 ID）。表からは `[N](#iN)` で飛ばす

### #15 UI 文言がすべて日本語のハードコード

**何が起きていたか** — UI 文言がすべて**日本語のハードコード**で、i18n の仕組みが無く、
`src/features/**` と `src/app/**` に文言が散在していた。エラーメッセージや確認ダイアログの文面もコード内に直書き。
一般公開を目指すと決めた（[basic-design/01-overview](basic-design/01-overview.md)）ので、
公開範囲が実質日本語話者に限られることが**もう起きているズレ**になった。

**どこまで進んだか** — **文言を `t()` とカタログに寄せた**（[features/i18n](features/i18n/design.md)）。
`src/` に残る日本語リテラルは書体の固有名詞 15 件と測定用文字列 2 件のみ。

**残り** — **言語は日本語 1 つのままなので、公開範囲が日本語話者に限られる点は解消していない**。
英語カタログと言語切替 UI は別作業として残る。

### #88 サイズと書体は、範囲を選ばないと何も起きない

**何が起きていたか** — 箱をクリックしてサイズ欄の数字を変えても、**何も起きなかった**。

同じパネルの中で**サイズと書体だけ振る舞いが違う**状態になっていた。

値を書く 3 つ（サイズ・書体・太さ）は**キャレットだけの状態を意図的に拒む** ——
`execCommand` はそこで要素を 1 つも作らず pending style を立てるだけで、
その pending style は数値欄がフォーカスを取り返した瞬間に捨てられ、`<font>` だけが残る（[#76](#i76)）。

箱をクリックしてサイズを変える —— が「何も起きないコマンド」に流れていた。

サイズについてはその約束が嘘だった。

**どう決着したか** — 範囲が無ければ**要素全体に効かせる**（2026-08-25 にユーザーが裁定。太さと揃える）。
何も選んでいないときの「大きくして」は箱についての話、というのがその根拠。
分岐は `applyToScope` の 1 箇所に `hasSessionRange` を足しただけ ——
3 つとも同じ理由で同じ規則に従うので、書き分ける場所は要らない。
[inspector/design.md](features/inspector/design.md) の

### #81 書式ボタンを続けて押すと 1 手の undo に畳まれる

**何が起きていたか** — U を押して 150ms 後に S を押すと `undoStack` が **1 しか増えなかった**
（1 秒以上あければ正しく 2 増える）。打鍵を 1 手に畳むための仕組みが、ボタン操作にもそのまま効いていた。
テキストセッションは**打鍵も書式コマンドも同じ `SetInnerHtmlCommand`** で記録するので、
「同じ uid なら畳む」だけでは両者を区別できない。

**どう決着したか** — **区別は触った要素の集合で付ける**。タイピングは要素を増やさず

`innerHTML` から uid を拾い、**集合が同じときだけ**畳む。
パースせず文字列を走査するのは、比べる 2 つが同じ作り方（`reindex` 直後の `innerHTML`）で

`innerHTML` は属性値の `"` をエスケープするので、パターンが当たるのは本物の属性か、
**スライドに文字として打たれた** `data-hse-uid="…"` だけ。
後者は最悪でも併合の判断を 1 回間違えるだけなので、安いほうを採った。

### #80 履歴が戻した markup まで「貼り付け」として洗っていた

**何が起きていたか** — 貼り付けの洗浄は MutationObserver に相乗りしている（[#12](#i12)）ので、
**Undo / Redo の復元も同じ観測を通る**。洗うと uid が総剥がしになり、
さらに次の Redo が「uid だけ違う」余計なコマンドを積んで redo を潰す
（実測: ⌘Z のたびに箱の中の uid が総入れ替えになり、⌘⇧Z が効かない）。
**この挙動は今回の変更以前からあり**、[#78](#i78) の「値まで一致するものは残す」が無かったぶん、
以前のほうが被害が大きかった。

**どう決着したか** — `useHistory` の `lastAt === 0` で印を立て、
`withUndo` と同じくマイクロタスクで下ろす（[#44](#i44) が「`execute()` が時刻を書き、
undo / redo / revoke が 0 に戻す」で引いた線をそのまま使う）。
実測: U → 1.1 秒 → S のあと ⌘Z で `undoStack` 6→5、strike だけ消えて `<u>` は残る。⌘⇧Z で 5→6。
uid の重複も欠落も無し。[editing-engine/design.md](features/editing-engine/design.md) の
「履歴が戻した markup も洗ってはいけない」。

### #79 編集中の ⌘Z がネイティブ undo に乗っ取られる

**何が起きていたか** — テキスト編集中の ⌘Z が `contenteditable` のネイティブ undo に食われ、
**アプリの履歴は動かないまま DOM だけが戻る**。

**どう決着したか** — 2 段構えで受ける。フレーム側 `document` の `keydown` で横取りして

保険が狙うのは履歴の辻褄合わせではなく「**取り返しのつかない状態にしない**」ところまで。
WKWebView ではネイティブ undo が勝ったままで、残りは [#89](#i89)。

`<div><span style="font-size:48px"><br></span></div>` になる。**ブラウザは正しい答えを
こちらに訊かずに出している。** それを貼り付けとして洗うと 0.2 秒後にサイズが剥ぎ取られ、
**次に打った文字は箱の既定に戻る**。色と蛍光も同じ。`<b>` だけ生き残るのは、
強調がもともと残す側だから。

**どう決着したか** — **線引きを値で引く**。箱の中身が既に宣言しているものと**値まで一致する**宣言は残す。
ブラウザが編集中に作るものは必ず箱の中にある run の複製なので常に通り、
Word の `font-size:99px` は通らない。**属性は一切緩めていない**
（Chrome は run を `data-hse-uid` ごと複製するので、割れた行の両方が同じ uid を名乗る）。

素朴な規則は実ブラウザで測って全部落ちた —— 「エディタのコマンド中だけスキップ」は
こちらが作るノードしか覆わない、「祖先が持つ宣言を残す」は 48px が前の行の**兄弟**にあるので効かない、
「裸の span はブラウザ製」は Google ドキュメントが裸の span を貼るので逆に効かない。

実測: `Hello` → 全選択 48px → 改行 → `X` を実キーで打つと `X` の computed `font-size` は **48px**
（修正前は 28px に戻っていた）。色・蛍光も次の行に引き継がれ、`insertHTML` で入れた
99px の span は `class` も 3 宣言も全部落ちる。
[editing-engine/design.md](features/editing-engine/design.md) の「ブラウザ自身の編集も洗ってはいけない」。
実クリップボード経由が未検証なのは [#93](#i93)。

### #72 テキストボックスの高さが中身に追従しない

<a id="i71"></a>
### #71 番号の行頭記号が枠からはみ出す

**何が起きていたか** — [#65](#i65) で書いた `padding-left: 1.2em`（箇条書きの慣習値）は、
**番号付きには足りなかった**。ユーザーのデッキで実測すると、76px の見出しを `1.` にすると
**マーカーだけで 89.02px** を要求し、1.2em（91.2px）は余裕がわずか **2.18px**。
枠線に接して見えるうえ、`10.` に届けば確実に外へ出る。

**どう決着したか** — **実測して決める**。`::marker` は箱を渡してくれない
（`getComputedStyle(li, '::marker')` が答えるのは種別と色だけ）が、
`list-style-position` の 2 つの値は**同じマーカーを違う場所に置く** ——
`outside` は行から外へ吊るすので文字は項目のコンテンツ端から始まり、
`inside` は行の中に置くので文字はマーカーの後ろから始まる。
**その差がマーカーの送り幅そのもの**なので、一時的に `inside` へ倒して
文字の開始位置がどれだけ動いたかを測り、必ず元へ戻す（`measureMarkerAdvance`）。
書体・字数・カウンタ種別に依らず答えが出る。確保するのは**実測値 + 0.3em**
（文字に接して見えないための余白であり、`1.` の一覧が `10.` に届いたときの 2 桁目の分でもある）。
単位を `em` にしたので、あとで文字サイズを変えてもマーカーと一緒に動く。
測れなかったとき（項目がまだ無い等）だけ 1.2em に落ちる。
jsdom は `Range` を持つが geometry を持たないので、実装側で「測れなかった」を返す。
実測（Claude Code 基礎講座 / h1 76px）: 修正前 1.2em = 91.2px で余裕 2.18px、
修正後 1.48em = 112.48px で余裕 23.46px。

<a id="i70"></a>
### #70 Enter で確定すると末尾に空の div が残る

**何が起きていたか** — Enter は `contenteditable` では確定ではなく `insertParagraph` を走らせる
編集コマンドで、**ブロックを 1 つ生む**。実デッキで「aaa」→ Enter と打つと
`aaa<div><br></div>` が残り、子が 2 つなので単独ラッパーの規則（[#67](#i67)）が対象外にしていた。
しかもその空 div は `reindex()` で uid を貰うので**独立して選択できる要素になり、
箱の中に選択枠が 2 つ出る**。

**どう決着したか** — **落とす**（2026-08-25 にユーザーが裁定）。
キーを横取りする手は無い —— ステージのフレームはスクリプトを走らせないので WebKit は
ホストが張ったリスナを発火させず（[ADR-0002](adr/0002-edit-preview-separation.md)）、
`defaultParagraphSeparator` は**どのタグを生むか**しか選べない。だから後から落とす。

落とすのは**末尾だけ、かつ中身が読めないものだけ**。段落のあいだの空行はユーザーが空けた間隔なので残し、
属性を持つブロックも残す（`justifyCenter` が単一行の箱に置く `div style="text-align:center"` を
剥がすと揃えた行が動く）。uid だけは属性に数えない（`reindex` が全要素に押すので何も区別しない）。
単独ラッパーを畳む**前**に走らせる —— 末尾を落とした結果が単独ラッパーになることがあるため
（`<div>aaa</div><div><br></div>` → `<div>aaa</div>` → `aaa`）。
実測（Claude Code 基礎講座 / 15 スライド。挿入 → ダブルクリック → aaa → Enter → 外をクリック）:
修正前 `aaa<div data-hse-uid="el"><br data-hse-uid="em"></div>` → 修正後 `aaa`。

<a id="i69"></a>
### #69 ダブルクリックで編集に入ってもキャレットが立たない

**何が起きていたか** — キャレットは「フォーカスされたフレームの、フォーカスされた要素」にしか描かれない。
ところがセッションを開くきっかけの press は `handleLayerPointerDown` が**ホスト側**の
`.stage-interaction` にフォーカスを載せており（ダブルクリックなら 2 回）、
`startTextEditing` は `element.focus()` しか呼んでいなかった。
**Chromium は中の要素を focus した副作用でホスト文書のフォーカスも iframe へ動かす**ので
1 行で足りていたが、それはエンジンの親切に頼っていただけで、**WebKit はその面倒を見ない**。

**どう決着したか** — `holdTextFocus()` を新設し、**外から内へ 3 段**で渡す
（iframe 要素 → フレームの `window` → 要素そのもの）。順序は逆にできない ——
前 2 つはフレーム側の `activeElement` を `body` に戻すため。
直前に `contenteditable` を付けた要素はスタイル再計算が済むまでフォーカスできないと
見なされうるので、先頭で `offsetHeight` を読んで recalc を流す。

あわせて `placeCaret` の穴を塞いだ —— `caretRangeFromPoint` は**文書に対して**答えるので、
箱の padding や行間に当たった点では隣や親の range が返る。そのまま張ると
`contenteditable` でない場所にキャレットが立ち、何も描かれず打鍵も落ちる。
`element.contains()` を通らない点は捨てて末尾に落とす。
**端の丸め方はエンジンごとに違う**ので、Chromium で出て WKWebView で出ない、
という形で表に出ていた可能性が高い。
`removeAllRanges` + `addRange` は `selection.collapse` に置き換え、
フレームの選択が一瞬 0 本になる状態を経由しないようにした。
実測（Chromium）: `hostActive=IFRAME.stage-frame` / `frameHasFocus=true` /
`frameActive=DIV uid=e5` / `caret-color=rgb(56,132,255)` / `range=(DIV,0) collapsed inside=true`。

### #68 挿入したテキストボックスが移動もリサイズもできない

**何が起きていたか** — 挿入した箱はそのまま編集セッションに入っていたが、
編集モードでは操作レイヤが `pointerEvents:none` になり Overlay もハンドルを描かなくなるので、
**挿入直後の箱は移動もリサイズもできなかった**。

**どう決着したか** — **PowerPoint と同じ二段階**（選択 → ダブルクリックで編集）にする
（2026-08-25 にユーザーが裁定）。これは
[editing-engine/decisions.md](features/editing-engine/decisions.md) #74 / #75 が
意図的に組んだ 3 つの仕掛けを同時に壊すので、**4 点セット**で作り直した ——
挿入は選択のみ／空箱への再入場を「挿入直後の 1 件」限定で許す
（`isTextEditable` 本体は触らず、呼び出し側で `isUntouchedTextBox` を `||` する。
緩めるとデッキ由来の空 div まで編集対象になる）／プレースホルダを選択中にも描く
（CSS セレクタから `contenteditable` を外し、ガードを script 側へ降ろす。[#46](#i46) と同じ考え方）／
破棄の合図を「セッション終了」から「選択が離れた・スライドが変わった・モードが変わった・
デッキの形が変わる」へ移す。

そのうえで、この変更が開けた穴を 3 つ塞いだ。

1. **足場を落とす door** —— 印だけで描かれるようになった以上、markup を写す door すべてで
   足場を落とす必要がある。`slideMarkup`（履歴）と `stripEditorMarks`（複製）が落としていなかったため、
   ⌘D と ⌘Z で「消えないプレースホルダ」が焼き付いた。判断の正は `bridge.ts` の
   `SCAFFOLD_ATTRIBUTES` に集約（uid は door ごとに扱いが逆 —— 履歴では残す・複製では落とす）
2. **破棄の合図が届かない経路** —— プレビュー切替は空 div が保存・書き出しに乗るので
   不変条件 2 に触れていた。スライドの複製・削除・並べ替えは `slide:changed` が出ないので
   コマンドの構築時に始末し、連続挿入は挿入の冒頭で前の pending を始末する
3. **`revoke` の二重 revert** —— `engine` に `restoring` フラグを置き、復元中の revoke を no-op にした
   （undo の publish → revert の順序は影響範囲が広いので変えていない）

Esc（ダブルクリックで入って一文字も打たずに抜ける）は**箱を残して選択状態に戻す**
（2026-08-25 にユーザーが裁定）。pending は保ったままにする —— 消すと空箱への再入場が 1 回しか使えない。

### #67 テキストボックスの下に要らない div が 1 枚増える

**何が起きていたか** — `contenteditable` の中で Enter を押すと、ブラウザは新しい行を `<div>` で包む
（`defaultParagraphSeparator` が選べるのは div か p かだけで、**包まない選択肢は無い**）。

### #66 空のテキストボックスに点滅カーソルが出ない

**何が起きていたか** — 空の要素は**行ボックスを持たない**のでキャレットの立つ場所が無く、
何も描かれなかった。Chromium 実測（本番と同じ `sandbox="allow-same-origin"` のフレーム・同じ注入 CSS）では
`document.hasFocus()` も `activeElement` も `(div, 0)` の collapsed range もすべて正しいのに、
**点滅するものだけが無い**。`<br>` を 1 つ入れると出た。
プレースホルダを通常フローから外すだけでは出ない。

**どう決着したか** — 3 つ入れた。

1. セッションが開くとき、空なら `<br>` を 1 つ**貸す**（印付き）。最初の打鍵でブラウザ自身が消し、

2. プレースホルダの `::before` を `position:absolute` にする。フロー内では行頭の実インラインボックスになり、

3. **空のあいだだけ** `caret-color` をエディタの色にする。挿入する箱は `color:#14161a` を
   決め打ちで持つので、暗いデッキでは溶けていた

要素側に `position:relative` は当てない —— このセレクタはセッション中に中身を消した要素にも当たるので、
デッキが絶対配置している見出しが**最後の 1 文字を消した瞬間に飛ぶ**ことになるため。

### #65 箇条書きにしたリストが箱からはみ出す

**何が起きていたか** — リスト化した瞬間に、箱から出ていく道が 2 つあった
（挿入する 520×90 の箱・`font-size:28px` で Chromium 実測）。

- **下へ** —— UA スタイルの `ul { margin-block: 1em }` が 28px × 2 を足すので、

- **左へ** —— `list-style-position:outside` の行頭記号は**リスト自身の
  `padding-inline-start` の中**に描かれる。`* { margin:0; padding:0 }` のリセットを持つデッキは
  その余白が無いので、記号が**負の x**（箱の完全な外）に落ちた

**どう決着したか** — **左と縦の両方を直す**（2026-08-25 にユーザーが裁定）。

### #44 テキスト編集中に太さ・行揃えを触ると打った文字が undo 履歴から消える

**何が起きていたか** — 見出しをダブルクリックして文字を打ち替え、そのまま右ペインの
**行揃え**か**太さ**を触ってからセッションを抜けると、undo スタックに残るのは 1 手だけ。
元に戻すと行揃え（または太さ）は戻るのに、**打った文字は戻らず、元に戻すも無効になる**。
[#37](#i37) の調査中に実測で見つけた（記入日と同日に解決）。

`EditStage` は履歴ストア**そのもの**を購読して `resyncTextBaseline` を呼んでいる。
これは「セッション中に Undo / Redo が走ったら基準を追従させる」ためのものだが、
zustand の購読は `execute()` の push でも発火する。push で基準を進めると、
**そこまでの入力が「その入力に触っていないコマンド」に渡ってしまう** —
入力はどちらのステップにも属さなくなり、セッション終了時の `commitTextSession()` は
`html === baseline` で早期 return する。

被害を受けるのは、セッション中に到達できて `commitTextSession()` を通さない経路。
文字書式パネルの**太さ**（`applyToElement`）と**行揃え**（`alignElement`）の 2 つで、
範囲に当たるものは `withUndo` が前後で確定するので無事だった。
（`setGeometry` も同じ形だったが、[#37](#i37) で位置とサイズがセッション中に描かれなくなったので
現行 UI からは到達しない。）

**どう決着したか** — 2 つ入れた。

1. **`resyncTextBaseline` を Undo / Redo / revoke のときだけ効かせる。**
   判定は `useHistory` の `lastAt` — `execute()` が時刻を書き、`undo` / `redo` / `revoke` が 0 に戻す。
   **ストアが既に引いている線**なので、同期させ続ける 2 つ目のフィールドも、
   呼び出し側が渡し忘れられるフラグも要らない
2. **要素スコープ（太さ・行揃え）が `execute` の前に `commitTextSession()` を通す**（`asOwnStep`）。
   1 だけでも入力は消えなくなるが、**順序としてこちらが正しい** —
   行揃えは要素の中のリストノードにも書くので、後から積む `SetInnerHtmlCommand` の
   マークアップにその上書きが含まれ、入力を Undo すると `reindex()` が uid を配り直して
   下のスタイルのコマンドが戻す相手を見失う

回帰テストは**片方ずつ外すと落ちる**ことを確かめてある
（`richText.test.ts` が 1、`inspectorElementScope.test.ts` が 2）。
仕組みは [features/editing-engine](features/editing-engine/design.md) の「履歴の基準」、
パネル側の作法は [features/inspector](features/inspector/design.md)。

**副作用として了解したこと** — セッション中に開くパネルは文字書式 1 枚になる

1. 取り込んだ直後は出にくい
2. テキスト編集のために要素をダブルクリックし、フォーカスを外した後に**しょっちゅう**出る
3. ただしダブルクリックしても出ないことがあるので、**ダブルクリック単独が原因ではない**

共通していたのは「ジェスチャの途中で `pointercancel` 相当のことが起きると復帰できない」形。
`onPointerCancel` が `handleLayerPointerUp`（`releasePointerCapture` + `gestures.end()` + `commit()`）に
繋がっていたため、**どんな理由のキャンセルでも即座にドラッグが確定していた**。

原因候補は 4 つ挙がっていた —
(a) ダブルクリックがホスト文書に残した選択範囲を掴み、Chromium が選択テキストの
ネイティブドラッグを開始して `pointercancel` に化ける /
(b) Windows の精密タッチパッド・ペンがジェスチャ判定で `pointercancel` を投げる /
(c) `setPointerCapture` がレイヤ外で黙って外れる（`lostpointercapture` を拾っていなかった）/
(d) WebView2 で既定有効な Tauri の drag-drop ハンドラ。
2026-08-23 に macOS の Chromium（Playwright の実マウス）で 15 枚のデッキを取り込み・選択・
120px のドラッグ・リサイズ・回転・矢印キー移動まで通したが**再現せず**、Windows / WebView2 固有と見ていた。
ただし**候補 (a) の前提条件が成立していることは macOS でも確認できた** —
テキストセッションを Esc で抜けた後、ホスト文書の選択が空のまま `isCollapsed: false` で残っていた。

**どう決着したか** — 計測を待たずに、**原因が何であれ効くもの**と**候補 (a)(b) を潰すもの**を
2026-08-23 にまとめて入れた（[features/editing-engine](features/editing-engine/design.md) の
「`pointercancel` も『取り消し』であって『完了』ではない」以下、
[decisions.md](features/editing-engine/decisions.md) #64・#65）。

1. **`pointercancel` を `cancel()`（巻き戻し）へ繋いだ** — 症状の被害側。
   キャンセルされたドラッグが確定しなくなるので、「ピクッと動いて残る」は消える
2. **`.stage-interaction` に `touch-action: none` / `user-select: none` と、`pointerdown` の
   `preventDefault()`** — 候補 (a)(b)。[#8](#i8) の `.pane-divider` と同じ処方
3. **`releaseTextFocus` でホスト文書側の選択も畳むようにした** — 候補 (a) の引き金そのもの

**2026-08-25、Windows 実機で検証して再現しないことを確認した。**
症状が消えただけでなく**ドラッグが最後まで追従する**ので、手 1 だけが効いた
（＝キャンセルは起き続けているが確定しなくなっただけ）のではなく、
**手 2・3 が原因側を潰した**と読める。ただし 3 手を同時に入れているので、
**どれが決め手だったかまでは切り分けていない**。
候補 (c)(d) の計測（`dragstart` / `pointercancel` / `lostpointercapture` と `event.pointerType` のログ）には
進まずに済んだ。同じ症状が再発したら、そこから再開する。

### #40 「太さ」のプルダウンが開かない

**何が起きていたか** — 右ペインのフォントのすぐ下にある「太さ」の `<select>` を押しても
**リストが出ず、太さを選べなかった**。すぐ上のフォントのプルダウンは開く。

太さの `<select>` にだけ `onMouseDown={(e) => e.preventDefault()}` が付いていた
（`src/features/TextFormatControls.tsx`）。
Chromium / WebView2 では `<select>` の `mousedown` の**既定動作がポップアップの表示**なので、
`preventDefault()` はリストを開かせない。`FontSelect` には `onMouseDown` が無く、
そちらは開いていた — **差はこの 1 行だけ**。

**どう決着したか** — `<select>` の `onMouseDown` を外した（周りの `<button>` のものは**残す**）。

`preventDefault` はテキストセッションの選択範囲がフォーカス移動で消えるのを防ぐために
周りのボタンと揃えて付いたものだが、**ボタンとは既定動作そのものが違う** —
ボタンのそれはフォーカスの移動なので止める意味があり、`<select>` のそれはポップアップなので
止めると機能が消えるだけになる（[inspector/decisions.md](features/inspector/decisions.md) #52、
[design.md](features/inspector/design.md) の
「`mousedown` の既定動作を止めてよいのは、それが『フォーカスの移動』だけのとき」）。

外しても範囲は失われない。範囲を守っているのは `preventDefault` ではなく、
`pointerdown` の時点でのスナップショットとコマンド実行前の復元
（`src/core/editing/richText.ts`）。フォント側が確認ボタン無しで成立しているのがその証拠で、
太さはそもそも要素スコープ（`applyToElement`）なので範囲を使いもしない。
**キーボード（Tab → ↑↓）は塞がっていなかった** — 適用は `change` に載っていて、
塞がれていたのはマウスの経路だけだった。

回帰テストは `src/features/inspectorWeight.test.ts`（[test.md](features/inspector/test.md) 104〜108）。
**ポップアップが実際に開くところは自動では見えない** — ネイティブの `<select>` のリストは
ブラウザが DOM の外に描くので、jsdom にも、当時の CDP による実マウス検査にも映らなかった。
テストが固定しているのは「押下の既定動作が生きていること」と、
「外したせいで選択範囲・当たる先・Undo が変わっていないこと」。

### #39 行揃えの「両端」が何も変えない

**何が起きていたか** — 行揃えの 4 つ目「両端」を押しても、見た目が変わらなかった。
**書き込みは行われていた** — `alignElement` が `text-align: justify` を
`SetInlineStyleGroupCommand` で要素に書き、リストがあれば `ul` / `ol` / `li` にも配り、
ボタンも点灯していた（`li` の computed が 3 つとも `justify` になることを実測で確認）。
効いていなかったのは **CSS の側**。

**実測（2026-08-24、`samples/generic-deck.html` / headless Chrome 151）**

| 測ったもの | 数値 |
|---|---|
| 測定した文字箱 | 12 個（h1 / h2×3 / p×4 / li×3 / .metric>div×3） |
| `justify` で行の右端が動いた箱 | **0 / 12** |
| 折り返しのある箱 | **0**（h1 / h2 / p / li は全部 1 行。`.metric>div` の 3 行は別々のブロック＝各行が最終行） |
| 参考: `中央` が動かす量 | 225〜472px（8 箱） |
| 参考: `右` が動かす量 | 450〜944px（8 箱） |

**折り返す長文を入れれば効く**（`p`、24px、行幅 1120px、4 行）。
日本語は各行の凹み 18.62 / 41.91 / 18.39px が 0 になり、英語は 51.89 / 27.37 / 33.33px が 0 になる。
**最終行は仕様どおり動かない**。移動量は行幅の 3.7〜4.6% で、デッキの本文がそこまで長い場合に限られる。

**`text-align-last: justify` を併記すると 12 個中 8 個が動く。** ただし動き方は
「4 文字の見出し『主要指標』を 1120px に散らす」= **均等割り付け**で、
ラベル「両端」とも CSS の両端揃えとも別物になる。

**どう決着したか（2026-08-24）** — **ボタンを畳んだ**。`ALIGNMENTS`
（`src/features/TextFormatControls.tsx`）から `justify` の行を、`ja.ts` から
`inspector.alignJustify` を落とした。行揃えは 左 / 中央 / 右 の 3 つになった。
判断の詳細は [inspector/decisions.md](features/inspector/decisions.md) #51。

**`justify` の経路は残した。** `chosenAlign` / `listAlignmentStyle` は `justify` を
これまでどおり扱う — **デッキ自身が `text-align: justify` を持つ**要素を箇条書きにすると、
`carryAlignmentIntoLists` が computed からその値を受け取って配るため。
ここを消すと、両端揃えのデッキが箇条書きにした瞬間に左へ落ちる。
`listOverrides.test.ts` の該当ケースも、名前をその意味に直したうえで残した。

**払った代償** — **デッキ由来の `justify` はどのボタンにも当たらない**。
`shownAlign('justify')` は `justify` を素通しするので、両端揃えを宣言しているデッキの要素を選ぶと
3 つとも消灯し、[#32](#i32) の症状（揃っているのに未選択に見える）が **justify のデッキにだけ残る**。
`左` に倒して点ける案は採らなかった — 要素が持っていない選択を UI が主張することになり、
続けて `左` を押すと「何も起きていないのに上書きが増える」。
意図した結果だと分かるよう、[inspector/test.md](features/inspector/test.md) ケース 103 に固定した。

**この調査で別の課題が 1 件出た。** 箱が中身の幅まで縮んでいると行揃えがどれも効かない（[#41](#i41)）。
両端だけの問題ではなかった、というのがこの調査の副産物。

### #38 位置とサイズだけリアルタイムに反映されない

**何が起きていたか** — 右ペインの X / Y / 幅 / 高さ / 回転に数字を打っても、
**打っている間はステージが動かなかった**。Enter を押すかフォーカスを外した瞬間に飛ぶ。
数値のスピナー（上下の矢印）も同じで、1 つずつ増やしながら合わせる、という使い方ができなかった。
`GeometryPanel` が使っていたのは確定が `onBlur` と Enter だけの `NumberField` で、
余白・角丸は [#21](#i21)、文字サイズは [#26](#i26) で `LiveNumberInput` へ移ったのに、
**位置とサイズだけがその移行から取り残されていた**。

**どう決着したか** — **`LiveNumberInput` へ寄せ、`NumberField` は廃止した**（2026-08-24）。
インスペクタの数値欄はこれ 1 つになった。機械的な置き換えでは済まない点が 3 つあり、
それぞれ別の場所で潰している
（[inspector/design.md](features/inspector/design.md) の「位置とサイズも打つそばから当たる」）。

- **履歴のたたみ込み** — `StyleSnapshotCommand` に**名前付きの畳み込み**を足した。
  畳むのは merge key（`geometry:<欄>:<uid>`）を渡したものだけで、
  ジェスチャ（移動・リサイズ・回転・トリミング）は渡さない — あちらは `end()` の時点で
  すでに 1 コマンドとして到着するので畳む必要が無く、無条件に畳むと
  **少し間を空けた 2 回のドラッグが 1 手になる**（併合窓は 800ms）。
  キーに欄の名前を入れているのは、X / Y / 回転が同じ `transform` を書くので
  `SetInlineStyleCommand` のようにプロパティ集合では区別できないため
- **巻き戻し** — 畳んでも `before` は**最初のもの**を残す。でないと Undo が 1 打鍵前にしか戻らず、
  [#24](#i24) と同じくデッキが持っていなかった `width` / `height` が焼き付く。
  切り抜き済み画像の `placement` も同じスナップショットに入っているので、枠と画像が 1 手で一緒に戻る
- **基準値** — 打鍵のたびに要素が動くので、基準を run の最初に測ると 2 打鍵目が倍動く
  （X を `1` → `12` と打つと 13 に着く）。書き込みを
  [`core/editing/geometry.ts`](../src/core/editing/geometry.ts) へ出し、**毎回その場で測る**ようにした。
  待つのをやめたことで、`NumberField` が持っていた「focus の瞬間に uid と基準値を退避する」仕掛けも
  丸ごと不要になった — 書き込みがフォーカスを保ったまま終わるので、
  **A に打った数値が B に当たる**状況そのものが起きない

**ついでに直したもの** — 欄の文字列は**フォーカスがある間ユーザーのもの**にした。
要素は渡した数にいつも落ち着くとは限らず（`box-sizing: content-box` の箱に `width: 150px` を書けば
padding のぶん太って返る）、その答えで焦点のある欄を描き直すと**打っている最中の桁が消える**。
`LiveNumberInput` を使う既存の欄（余白・角丸・枠線の太さ・文字サイズ）も同じ扱いになる。

### #36 文字色・蛍光色に適用ボタンもパレットも無い

**何が起きていたか** — 「文字色」と「蛍光」の欄が、それぞれ OS 標準の `<input type="color">` ひとつだけで、
色を**変えた瞬間にしか**当たらなかった。困っていたのは 3 点。

1. **同じ色をもう一度当てられない** — `onChange` しか無いので、直前と同じ色を別の範囲へ塗り直す操作が無い。
   しかも文字色は制御入力で **直前に当てた色 = 入力の現在値**なので、
   いちばん塗り直したい色がいちばん発火しなかった。蛍光は `defaultValue="#ffe066"` の非制御で、
   既定の黄色を選ぶと初回から何も起きなかった
2. **パレットが OS のカラーピッカー** — デッキで使う色を並べておけず、毎回ダイアログを開いて選ぶ
3. **何のボタンか色見本だけでは分からない** — ラベルの「文字色」「蛍光」に全面的に頼っていた

**どう決着したか** — 2026-08-24 の `fd5294c`（`src/features/ColorPicker.tsx` を新設）で
**分割ボタン**にした。左半分が適用、右半分の ▼ がその場に開くパレット。
3 点はそれぞれこう埋まっている。

| 困りごと | 埋まり方 |
|---|---|
| 同じ色をもう一度 | 左半分の適用ボタン（`.color-apply`）が、バーの示している色をそのまま `onPick` に流す。`change` を介さないので、同じ色を何度でも別の範囲へ当てられる |
| パレット | 右半分の ▼（`.color-open`）で**プリセット 24 色がその場に開く**。OS のダイアログは「その他の色」の 1 行として残した（デッキは任意の色を使えるので、混ぜる場所は要る） |
| 何のボタンか | **インライン SVG のアイコン**にした（文字色 = 色のバーを敷いた `A`、蛍光 = マーカーペン）。バーだけが `currentColor` を外れて**実際の値**を描く。文言は `title` / `aria-label` へ回した |

**パレットの色の出所** — 「次の一手」が挙げた 3 案のうち **(a) 固定プリセット 24 色**を採った
（[decisions.md](features/inspector/decisions.md) #46、実体は `src/features/colorPalette.ts`）。

- **(b) デッキから集める**は退けた。集めた色は [ADR-0001](adr/0001-html-as-source-of-truth.md) の言う派生データになり、
  [06-data-model](basic-design/06-data-model.md) の「派生データはモデルに含めない」と
  「書き出しに漏らさない」責任を同時に負うことになる
- **(c) 最近使った色**は [ideas](ideas.md) #10 へ送った。`localStorage` に残すか・
  パレットの高さが可変になるか、が別の判断になるため
- 24 色の表は**文字色と蛍光で共用**する。2 つに分けると片方に足した色をもう片方が持たない状態が育つ。
  淡色の段が蛍光の守備範囲

仕様は [design.md](features/inspector/design.md) の「文字色と蛍光は『当てる』と『選ぶ』を分ける」、
判断は [decisions.md](features/inspector/decisions.md) #42〜#47。
検証は `src/features/colorPalette.test.ts` / `inspectorColor.test.ts`（[test.md](features/inspector/test.md) 3a・3b・77〜79）と
[inspector/test.md](features/inspector/test.md) ケース 80〜86（現在は `手動`）。
**ケース 85 がこの症状そのもの**（パレットを開かずに同じ色を 2 つ目の範囲へ）だが、
**手での確認は未了**なので、この 7 件はまだ通していない。

**この行が `対応中` のまま残っていたのは更新漏れ。** 実装は `fd5294c` に入っていて、
design.md / decisions.md / test.md も同じコミットで更新されていた。
2026-08-24 に状態だけを `解決` へ移した。

### #35 上付きボタンだけ、有効にしても点灯しない

**何が起きていたか** — 文字書式のボタンのうち、**上付き(`x²`)だけが押しても色が変わらなかった**。
B / I / U / S と段落ボタンは当たっているあいだ点灯するので、上付きだけが
「当たっているのか外れているのか UI から読めない」状態だった。

原因は 2 つあり、どちらも同じ形。

1. **ボタンが列の外にいた** — 点灯に要るもの(`active` クラス・`aria-pressed`・
   オンだと伝える title)は `FORMAT_BUTTONS` を描くループに書いてあるが、
   上付きだけ手書きの `<button>` として並べてあり、そのどれも持っていなかった
2. **エンジンに聞いていなかった** — `QUERIED_COMMANDS` に `superscript` が無く、
   そもそも状態が存在しなかった。[#27](#i27) の段落ボタン(inspector
   [decisions.md](features/inspector/decisions.md) #34)と同じ抜け

**どう決着したか（2026-08-24）** — **上付きを `FORMAT_BUTTONS` に入れ、`QUERIED_COMMANDS` にも足した**。
列に入れれば点灯・`aria-pressed`・title は自動的に付いてくるので、規則が 2 箇所に分かれない。
リストの外に残るのは**トグルでないもの**(書式のクリア)だけ。

`.format-button` の左右 padding も 0 にした。`box-sizing: border-box` の 28px 幅では
コンテンツ領域が 6px しか残らず、2 グリフの `x²` が隣のボタンへはみ出すため
(1 文字のラベルでも溢れてはいたが、目に見える害が出るのは 2 グリフから)。

判断は [inspector/decisions.md](features/inspector/decisions.md) #41、
回帰テストは `src/core/editing/richText.test.ts`(ケース 157)。
**点灯そのものが見えるかは unit では確かめられない** — `active` クラスが付いた結果は
実描画なので、そこは手で確認する([rules/development](rules/development.md) §2 の表)。

<a id="i34"></a>
### #34 挿入したテキストボックスの「テキストを入力」が実データとして残る

**何が起きていたか** — テキストボックスを挿入すると、箱の中に `テキストを入力` という文字が
**本物のテキストとして**入った(`textBoxHtml` が `t('content.newTextBox')` を埋めていた)。
打ち替えれば消えるが、**打ち替えなければ残る** — 挿入したまま別の作業に移れば、
エディタが選んだ言葉がそのままユーザーのスライドに残り、書き出した HTML にも入った。
設計書([i18n/design.md](features/i18n/design.md))は「どうせ書き換えられる placeholder」を
前提にしていたが、書き換えられない場合を勘定に入れていなかった。

**どう決着したか（2026-08-24）** — **箱は空で入れ、プレースホルダは編集ステージが描く**。
挿入すると同時にテキストセッションへ入り、編集中の空の要素には注入 CSS の `::before` で
`テキストを入力` を薄く描く。`::before` の `content` は DOM に無いので、
シリアライズ・複製・書き出しのどこにも入りようがない(不変条件 2)。

**一文字も入らずに終わった箱は、挿入ごと取り消す**(`revoke()`)。
Undo ではなく履歴からの取り下げなので、頼んでいない箱が redo に残らない。
間に別のコマンド(空の箱を動かした・書体を選んだ)が積まれていたときだけ、削除を 1 コマンドとして積む。
**消すのは挿入した直後の 1 件だけ**で、ユーザー自身の文章を全部消して抜けた要素は残す。

詳細は [editing-engine/design.md](features/editing-engine/design.md) の
「新しいテキストボックスは空で入る」、判断は [decisions.md](features/editing-engine/decisions.md) #74 / #75。
`src/core/editing/textBox.test.ts` に 6 件の回帰テストを置いた
(空で入ること・取り消しで履歴が空に戻ること・文字が入った箱を消さないこと)。
**プレースホルダが実際に描かれるかは unit では見えない**(CSS の適用は実ブラウザだけの話)ので、

### #32 行揃えの「左」が触っていない要素で点灯しない

**何が起きていたか** — 誰も行揃えを触っていない要素を選ぶと、行揃えの 4 段の**どれも点灯しなかった**。
実際には左に揃っているのに、UI は「まだ何も選ばれていない」ように見えた。
原因は `TextFormatControls.tsx` が `styles['text-align'] === value` と computed をそのまま比べていたこと。
**未指定の computed は `left` ではなく `start`** なので、4 つのどのボタンの値とも一致しない。

**どう決着したか（2026-08-24）** — **表示のときだけ、論理値を物理の側に直してから比べる**。
`shownAlign()`（`src/features/styleValues.ts`）が `start` / `end` を要素の `direction` で
`left` / `right` に解決し、物理値と空文字はそのまま通す。
`direction` は**インスペクタが読む** `READ_PROPERTIES` に足した — Format Painter が**塗る**白リストには足さない
（運ぶと、塗るだけのつもりが文字の流れる向きまで変わる）。

**RTL は「文字が実際に寄っている側」を点ける。** ボタンのラベルは 左 / 中央 / 右 という物理の名前なので、
`direction: rtl` の要素で `start` は**右**。記入時に「決めてから入れる」としていた点で、
[decisions.md](features/inspector/decisions.md) #40 に残した。

**書く側は変えていない。** `chosenAlign()`（`listOverrides.ts`）は `start` を
「誰も選んでいない」として扱ったままなので、箇条書きを押しただけのデッキに上書きは増えない（[#27](#i27)）。
直したのは表示だけで、**書き出す HTML は 1 バイトも変わらない**。

**直る前に落ちることを確かめた。** smoke に 2 件足し、修正前は
「点灯なし」で落ち、修正後は「左」で通ることを見た（[inspector/test.md](features/inspector/test.md) ケース 76）。
Chrome の computed が本当に `start` であることも前提として固定してある
— ここが `left` を返す実装では、点灯のテストは何も守らずに通ってしまう。

### #31 書式のコピーもサイズ・色がリストの中まで届かない

**何が起きていたか** — [#27](#i27) で**行揃えだけ**をリストの中まで配ったが、
「リストが継承を遮る」という問題そのものは残っていた。
デッキが `ul` / `li` を型セレクタで名指していると、親要素へのインライン上書きは
継承でしか届かないので必ず負ける — カスケードは「どの宣言が強いか」を問う前に
「この要素に宣言が当たっているか」を見るため、親がインラインでも関係ない。

症状は 2 経路にあった。**Format Painter だけではなく、
インスペクタの文字色・サイズ・フォント・太さの欄も同じ壁に当たっていた**
（記入時は Format Painter だけを見ていた）。中身が全部リストの箱では、
サイズ欄が**何も動かさない**ぶんこちらの症状のほうが重い。

**実測（2026-08-24、サンプルデッキ）** — 記入時は未実測だったが、
`ul { font-size: 26px; line-height: 2 }` に対して**両方とも起きていた**。
`h2` を箇条書きにして箱を選び、それぞれの経路でサイズを変えたときの
`getComputedStyle(li).fontSize`：

| 経路 | 修正前（箱 / 行） | 修正後（箱 / 行） |
| --- | --- | --- |
| 書式のコピー | 32px / **26px** | 32px / 32px |
| インスペクタのサイズ | 60px / **26px** | 60px / 60px |
| 文字色（デッキが `ul` を名指していない） | 届く | 届く。**上書きは書かれない** |

**どう決着したか（2026-08-24）** — **測ってから降ろす。**
`listAlignment.ts` を `listOverrides.ts` に改め、要素スコープの書き込みが
すべてそこを通るようにした。詳しくは
[features/inspector](features/inspector/design.md) の
「要素スコープの上書きは、リストの中まで届かせる」、
[decisions.md](features/inspector/decisions.md) #37〜#39。

1. **新しい値を要素へ一時的に当て、各リストノードの computed を
   要素自身の computed と比べる**。一致すれば継承が通っているので**何も書かない**、
   食い違えばそのノードに直接書く。書き込みはコマンド外で、`commit()` を呼ばないので
   ドキュメントストアには漏れない
2. **比較の両辺を computed で取る**。インスペクタは `#ff0000` を渡すがフレームは
   `rgb(255, 0, 0)` と答えるので、生の入力値と比べると全デッキの全リストに色の上書きが増える
3. **直しながら文書順に測る**。`ul` を直せば `li` は継承で届くので、
   デッキのルール 1 本に対して上書きは 1 つで済む
4. **降ろすのは継承プロパティだけ**（`color` / `font-family` / `font-size` /
   `font-weight` / `line-height`）。ボックス系は継承しないので、
   `li` が箱と食い違うのは正常であり、遮りと読むと行ごとに背景が塗られる
5. **インスペクタの要素スコープも同じ経路に載せた**（`applyToElement`）。
   ボックス系の欄は `SetInlineStyleCommand` のまま

**「常に降ろす」を採らなかった。** 遮っていないデッキにも上書きが増え、
書き出した HTML にエディタ由来の宣言が要らないところまで残る。
**「いま `li` と箱の computed が一致していれば継承が通っている」という推定も採らなかった** —
デッキの宣言値がたまたま箱の現在値と一致しているケースを取り逃がす。

**記入時に挙げた「計算コストと見た目のどちらを取るか」は問題にならなかった。**
降ろすのは**ユーザーが明示的に値を指定したときだけ**で、
リストを作った瞬間には降ろさない（[decisions.md](features/inspector/decisions.md) #39）。
行揃えには「誰も選んでいない」を表す computed（`start`）があるが
**サイズ・色には無い**ので、リスト作成に載せると箇条書きを 1 回押しただけで
全デッキのリストに上書きが書き込まれる。

**残したもの** — 「サイズを変えてから箇条書き」と「箇条書きしてからサイズを変える」は
**同じにならない**（前者はデッキの `ul` 指定が勝つ）。
これはデッキ自身の CSS がそう書いている結果なので、意図的に受け入れた。

### #28 右ペインで行の余白をクリックしてもフォーカスが外れない

**何が起きていたか** — 右ペイン（インスペクタ）で、フォーカスが当たっている入力欄と
**同じ行のすぐ右**をクリックしてもフォーカスが外れなかった。別の場所を触ったつもりでも、
その欄が入力を受け続ける。

原因は `Field` が**行全体を 1 枚の `<label>`** で包んでいたこと。
`<label>` は `for` が無くても「最初の labelable な子孫」と暗黙に関連付き、
**その子孫へ click を転送する**。`.field` は 56px のラベル列 + `1fr` の grid で、
数値欄は `.spacing-number` の 64px などで伸びないため、
ラベル文字・56px 列の余り・入力欄の右の空白がすべて label の内側にあった。

**実測（2026-08-24、Chromium・実マウス）** — 記入時に「未実測」としていた派生も含めて確定した。
症状本体より**派生のほうが重い**（触っていない書式が変わる）。

| クリック位置 | 起きていたこと |
|---|---|
| 「行揃え」のラベル文字 | `click` が**先頭ボタン「左」に転送**され、触っていない行揃えが当たる |
| 行揃え行の右の余白 | 同上 |
| 「角丸」行の右の余白 | `blur` → `focus` が連続し、フォーカスが**戻る**（`activeElement` は数値欄のまま） |

`onMouseDown` の `preventDefault`（`TextFormatControls.tsx`）は mousedown しか止めないので
click 転送には効いていなかった。文字色行も先頭の `<input type="color">` が開く形になっていた。

**どう決着したか（2026-08-24）** — issue が挙げていた「`Field` が行のタグを選べるようにする」を採った。
詳しくは [features/inspector](features/inspector/design.md) の「行のタグは、載せるコントロールで決まる」、
[decisions.md](features/inspector/decisions.md) #35・#36。

1. **行は `<div>` になった。** ラベルセルは `<span>` で、コントロール側は
   `role="group"` + `aria-labelledby` でラベルと結ぶ。転送は起きず、名前は残る
2. **コントロールが 1 つの行だけ `<label for>` に戻す。** `Field` の `children` に
   関数を渡すと id を受け取れる形にし、ラベルセルだけがその 1 つに結び付く。
   「ラベルを押して入力欄へフォーカス」は保ったまま、**行の余白からは外れた**
   （不透明度・角丸・枠線の色・文字サイズ・フォント・太さの 6 行）
3. **`.field.compact`（位置とサイズ・辺ごとの余白・スライドサイズ）は `<label>` のまま。**
   入力欄が `width: 100%` で列を埋めるので、転送先を取り違える余白がそもそも無い

**修正後の実測（同じ手順）** — ラベル文字・余白のどちらを押しても行揃えは動かず、
角丸行の余白では `blur` だけが出て `activeElement` は `BODY` に落ちた。
「角丸」のラベル文字を押すと従来どおり数値欄にフォーカスが入る。

**残したもの** — 行揃えの「左」が触っていない要素で点灯しない件は別（[#32](#i32)）。

| スコープ | セッション要素の**内側**に `ul > li` を作る | 選択している uid **1 つだけ** |

|---|---|
| (a) `ul` の `padding-left` | `31.2px`（`1.2em`）→ 文字の中心が **+15.59px** 右へずれる（padding のちょうど半分） |

| (c) デッキ CSS の宣言 | `ul, ol, li { text-align: left }` を注入すると `li` の computed が `left` に落ち、中心が **-303.33px**。継承は完全に負ける |

[decisions.md](features/inspector/decisions.md) #31〜#34。

1. **`text-align` を要素とリストの全ノードへ書く**（`src/core/editing/listOverrides.ts`）。

2. **中央・右のときは `list-style-position: inside` と `padding-left: 0` も書く**（(a)(b)）。

3. **リストを作ったときも配り直す**（`richText.ts` の `run()`）。

4. **Format Painter も同じ配り方に載せた**（`pasteFormat`）
5. **段落ボタンにアクティブ表示を付けた**（`queryFormatState` にリストの 2 コマンドを追加）

セッションが開いていないと `richText.ts` の関数は何もしないので、
**「箱を選んで行揃え」が効かなくなる**（[decisions.md](features/inspector/decisions.md) #18 の EARS に対する退行）。

手で見るときは行を一度左に寄せてマーカー幅を実測し、それを引いてから比べる

**残したもの** — 行揃え以外の宣言（サイズ・色）は降ろしていなかった。
これは [#31](#i31) で「遮られていると実測できたノードにだけ降ろす」形で決着した。

### #22 インスペクタが要素の種類に関係なく全パネルを出す

**症状** — **右のインスペクタが要素の種類に関係なく全パネルを出す**。

種類で出し分けているのは `CropPanel`（画像のときだけ）だけだった。

**前半（2026-08-23）— 効かないものを消した。** **文字書式パネルは `isTextEditable` の要素にだけ出す**
ようにした（ダブルクリックがテキストセッションを開くかどうかと同じ判定）。

**「この要素でよく使うものを上に出す」という優先順位の問題**で、[#20](#i20)（詰め込み）と同じ道具でしか解けない。

**打った手** — [#20](#i20) と 1 つの設計にまとめ、**種別ごとの並び順**で解いた。
テキストなら文字書式、画像なら画像パネルが先頭に来て、それと位置とサイズだけが開いた状態で始まる。
図形は位置とサイズとボックス。判定は `isCroppable` / `isTextEditable` をそのまま使い、
**3 つ目の「画像とは何か」を書かない**。

**何が起きていたか** — テキスト編集中、**すでに選択されている範囲の上からドラッグして選択し直せなかった**。

**当初の見立ては外れていた。** ここには「編集フレームはスクリプト無効なので `dragstart` を潰せない
（[#2](#i2) と同じ壁）、直すなら注入 CSS（`injectEditorStyles`）側で当てる筋」と書いていたが、
**注入 CSS では直らない**。Blink / WebKit とも「押した点が選択範囲の中にあるか」で
ドラッグ種別を先に *Selection* と決めてしまい、`-webkit-user-drag` は
要素ドラッグ（DHTML / 画像）の判定にしか効かない。`user-select: none` は contenteditable 自体を壊す。

**どう決着したか** — **編集中要素の上もホスト側の 1 枚で覆い（`.overlay-text-shield`）、
選択をホストが引くようにした**（[features/editing-engine](features/editing-engine/design.md) の
「セッション中の選択もホストが引く」、[decisions.md](features/editing-engine/decisions.md) #66〜#68）。
フレームは press を一切見なくなるので、ネイティブドラッグが**起きようがない**。
`caretRangeFromPoint()` と Selection API を親から呼ぶのは WebKit でも動く経路
（キャレット配置が既に使っていた）。

`contenteditable` が無料でくれていたぶんは自前になった —
キャレット・2 連打で単語・3 連打で要素全体・Shift で伸ばす・枠外へ出たら直前位置で止める。
連打の回数は `PointerEvent.detail` が仕様上 0 なので、400ms / 4px の窓でホストが数える。

**捨てたもの** — 選択した文字をドラッグして移動する（ブラウザ標準の text drag-and-drop）。
ユーザー裁定で許容（decisions #67）。

**壊れていた状態は自動テストでは再現できない** — ヘッドレス Chrome は合成 press から
ネイティブドラッグを始めないため。かつてヘッドレスの自動テストを当てていた頃も、
それが守っていたのは**置き換えたあとの経路**であって、この症状そのものではなかった。
確かめるなら実マウスで手で触る（[rules/development](rules/development.md) §2 の表）。

**関連** — [#16](#i16) の候補 (a) が「実際に起きている」と言えた根拠の 1 つがこれだった。
編集セッション中のぶんは消えたが、#16 はセッションの無い状態で起きているので別物。

### #18 クリックしたつもりの数 px でオブジェクトが動く

**何が起きていたか** — 押して離すだけのつもりの操作で、指の震え数 px 分だけ要素が動いていた。
Undo で戻せるが、気づかないまま少しずつレイアウトが崩れる。
`handleLayerPointerDown` が pointerdown で即 `beginMove` し、`#moveSelection` が
`dx !== 0 || dy !== 0` で位置を書いていた — **ドラッグ開始のしきい値が存在しなかった**。

**座標系のせいで実害が拡大していた** — ジェスチャはステージ座標（デザイン px）で動く。
実測（2026-08-23）でズーム 46% 表示の 3 画面 px が、スライド実寸 **9.83px** の移動になっていた。
**縮小表示しているほど、画面上のわずかな震えが大きなズレになる。**

**どう決着したか** — 移動距離が**画面上 4px** を超えるまで `transform` を書かない
（2026-08-23、[decisions.md](features/editing-engine/decisions.md) #69）。
判定は既存の `moved` フラグの立て方を差し替えただけで、
「履歴に積むか」と「Alt の複製を起こすか」の両方にそのまま効く。

しきい値は**画面 px で測る** — 手の震えは物理的な距離なので、ステージ px に固定すると
46% 表示では画面上 1.8px しか吸収できず症状がほぼ残る。`beginMove` がジェスチャ開始時の
ズームを受け取り `4 / scale` ステージ px に換算する。越えたあとは**始点基準**で追従するので、
要素がポインタより 4px 遅れたまま付いてくることはない。

時間の遅延方式はトラックパッドで体感が悪いため退けた。

**広げた先** — 同じ日のうちに回転・リサイズへも広げた（[#29](#i29)）。トリミングのグリップだけが残っている（[#30](#i30)）。

### #24 リサイズを Undo しても `width` / `height` が焼き付いて残る

**何が起きていたか** — リサイズしてから ⌘Z すると、**サイズは戻るのに `width` / `height` が要素に残った**。
実測（2026-08-23、Claude Code 基礎講座デッキ）: 取り込み直後は `style` に `width` / `height` を

書き出した HTML にも残る。移動・回転の Undo は綺麗に戻っていた。

スナップショットより前に書かれることが無くなり、[#29](#i29) のハンドル・クリックも同時に潰れる。
`start` に入れる寸法は `boxOf()` から取っているのでピン留めの前後で変わらず、順序を変えても影響しない。

「ピン留めを `captureStyles` の後ろへ動かすだけ」でも #24 は直るが、
ハンドルをクリックしただけで寸法が焼き付くほうは残るので採らなかった。
ピン留めを消す案（`resizeKeepingAnchor` が毎フレーム寸法を書くので冗長に見える）は、
内容で伸びる箱の初回 reflow を実機で確かめずに消せないため見送った。

### #97 ドラッグ中の Shift が水平・垂直の固定にならない

**何が起きていたか** — オブジェクトをドラッグするとき、Shift を押しても水平・垂直に固定されなかった。

最初から PowerPoint と同じ意味だったので、**3 つのうち移動だけがずれていた**。

**どう決着したか** — 移動の Shift を**軸固定**に振り替えた（`fix/shift-axis-lock`）。

矢印キーが担う）。**移動中の吸着は常に効く**ようになった。
軸を固定しているあいだは、止まっているほうの軸を吸着の候補に出さない
（`snapToGuides` の `edges` にその軸だけ空配列を渡す）—— 出すと固定した軸から引き剥がされる。

設計は [features/editing-engine](features/editing-engine/design.md) の
「Shift はドラッグを軸に固定する」、キーの管轄の線引きは
[features/shortcuts](features/shortcuts/design.md) の「やらないこと」。

<a id="i98"></a>
### #98 箇条書きが効かないテキストボックスがたまにある

**何が起きていたか** — 箇条書きボタンが効くボックスと効かないボックスがあった。
原因は 1 つではなく、**編集ホストがどの要素になったか**で 3 通りに分かれていた
（Chromium で `samples/generic-deck.html` の実マークアップを実測）。

- **`<ul>` / `<ol>` がホスト** — `execCommand` は `true` を返すのに DOM が 1 バイトも変わらない。
  自分自身はアンラップできないため。`queryCommandState` は「リストの中」と答えるので、
  **ボタンは点灯したまま何も起きない**。デッキが元から持つ箇条書きは、遡上が `<li>` と `<ul>` を
  透過してスライドルートの手前で止まるので、必ずここに落ちる
- **`<span>` がホスト** — `display` に関わらず `false` を返して何もしない（Blink）。
  同じインライン級の `<strong>` / `<em>` / `<b>` / `<a>` / `<label>` は通るので、
  インラインだからではなく**タグの特別扱い**。デッキが span にブロック表示を与えていると起きる
- **`<p>` がホスト** — 効くが往復で壊れる。別の欠陥なので [#103](#i103) として切り出した

**どう決着したか** — リストを持てないホストは、コマンドの前に**ホスト要素そのものを建て替える**
（`fix/list-on-unlistable-hosts`、`src/core/editing/listHost.ts`）。同じ種類のボタンならリストを外し、
別の種類ならタグを差し替え、`<span>` / `<p>` は `<div>` にしてから `execCommand` に渡す。
uid は引き継ぐ（不変条件 6）ので、選択もセッションも履歴も箱を見失わない。
記録は `HtmlSnapshotCommand` 1 本で 1 undo ステップ
（`SetInnerHtmlCommand` は要素を名指しして**中身**を書き換えるので、要素が入れ替わる建て替えを表現できない）。

**編集ホストを一段上げる案は、測ってから捨てた。** スライドルートを一時的に `contenteditable` に
すれば `execCommand` はリストを外側から見られる。`<ul>` → `<ol>` はきれいに通るが、解除は
**空の `<ul>` + 行ごとの `<span style="font-size:26px">` + 改行の消失**を残す。さらにキャレット 1 点で
リストが 3 つに割れるので、**1 つだったテキストボックスが 3 つに増える** ——
uid で箱を指す前提（不変条件 6）と噛み合わない。

タグが変わるとデッキの `p { … }` / `ul { … }` が当たらなくなるので、差し替えの前後で computed を測り
**変わった宣言だけ**をインラインの上書きに書き戻す（ADR-0004）。リストを外すときは
行頭記号のための余白を落とす —— 落とさないと実測で `padding-left: 1.2em` = **31.2px** の
字下げだけが残った。書き戻す値は computed なので `line-height: 2` が `52px` で焼き付く点は、
インスペクタのブラシ（[#31](#i31)）と同じ性質として
[features/editing-engine](features/editing-engine/design.md) の「編集ホストがリストを持てるか」に明記した。

### #104 文字を全部消してフォーカスを外すと、その箱が二度と触れなくなる

**何が起きていたか** — ユーザーが実デッキ（`samples/local/claude-code-basics.html`）で見つけた
3 つの症状 —— キャレットが見えるタグと見えないタグがある・文字のない状態でフォーカスを外すと
テキスト編集が触れなくなる・親タグがあるとボックス自体にフォーカスが当たらず消える ——
は、どれも**同じ根**から出ていた。印（`data-hse-blank`）をセッション終了時に外していたので、

デッキが持ち込んだ空要素はこれまでどおり背景のまま
（[decisions](features/editing-engine/decisions.md) #52・#75 の一線は動かしていない）。
あわせて編集ステージ限定の CSS で空の箱に 24x16px の床を敷き、
⌘Z が印の付いた箱に文字を戻したときは印を貼り直す（`useHistory` の購読）。
実測は **0 / 262 が編集不能、7 / 262 が幅 0**（残りは元から 0x0 の要素と、
`min-width` が効かない SVG の `<text>`）。

**残っている穴** — 印は DOM にしかなく、保存される markup には入らない（`data-hse-*` は
シリアライズで落ちる）。**スライドを切り替えて戻る・保存して開き直すと、空の箱は
デッキの空要素に戻る**。区別を残すには markup に印を書くしかなく、それは不変条件 2 に触れる。

**原因は 3 つ重なっていた。**

1. **取り込みがランタイムを捨てる**（上記）。要素そのものが `<div>` に置き換わっているので、
   仮にスクリプトが動く場所でも受け取る相手がいない
2. **元のコンポーネントは `window.omelette.writeFile` の無い環境では読み取り専用。**
   書き出した HTML を素のブラウザで開いた時点で動かないのは**元からの仕様**で、
   **不変条件 2 の破れではなかった** —— 起票時の見立て（「取り込みか往復シリアライズで落ちている疑い」）は外れ
3. **Tauri が既定でドラッグを消費する**ので、アプリ内のプレビューでも WebView には届かない
   （[ADR-0011](adr/0011-native-file-drop.md)）。1 が無くても動かなかった

**どう決着したか** — コンポーネントを復活させるのではなく、
**エディタ自身の操作として作り直した**（`src/core/editing/imageFill.ts`）。

- **枠だと見分ける印は持たない。** `data-hse-*` はシリアライズで全部落ちる（`stage/bridge.ts` の
  `cleanElement`）ので、印は**最初の保存までしか保たない**。そこで操作のほうを一般化し、
  **選んだ箱の中身を画像に差し替える**形にした。写真枠は「一番それを欲しがっている箱」でしかない
- **入口は 3 つ** —— 箱に画像ファイルを落とす / 箱を右クリックして「画像を入れる」を選ぶ /
  インスペクタの画像パネルのボタン。3 つとも `fillSelectionFromPicker` / `fillSelectionFromDrop` を通る。
  **当初の本線はダブルクリックだったが、2026-08-26 に右クリックメニューへ移した** ——
  ジェスチャの意味が箱の中身で変わる形をやめたため
  ([editing-engine](features/editing-engine/decisions.md) #109)
- **ドロップは Tauri のネイティブイベントで受ける**（[ADR-0011](adr/0011-native-file-drop.md)）。
  HTML5 の `drop` はどこに書いても発火しない
- **クリックが枠に届かない問題も直した。** キャプションが `inset:0` で枠全面を覆っていたため、
  枠へはパンくずでしか行けず、ダブルクリックはプレースホルダ文言にテキストセッションを開いていた。
  `pointer-events:none` を付けた（元は shadow DOM の中で掴めなかったので、**元の挙動に戻す変更**でもある）

**残っている穴** — スライドの余白に落としたときは何も起きない（[ideas](ideas.md) #16）。
デッキ本来の `<image-slot>` が**書き出した HTML で動く**ようにはなっていない ——
それは omelette ランタイムの機能で、このアプリが引き取れるものではない。
書き出した HTML の写真枠は、エディタで入れた `<img>` か、破線のプレースホルダのままかのどちらか。

### #102 移動した要素がポインタで触れなくなる（切り取り・重なり）

**何が起きていたか** — 移動させたボックスが、以降クリックで選択できなくなる。
起票時は「**単色のオブジェクトの裏側**へ回すと選べない」と書き、原因を
「ヒット判定が `elementFromPoint` だけで、返るのは最前面の要素」と見ていた。
**それは同じ症状の別の道で、報告された症状の原因ではなかった。**

実際の道は 3 つある。確認用デッキ（`samples/local/claude-code-basics.html`）の 12 枚目で、
`overflow:hidden` を持つカードから外へドラッグした見出しを実測した:

| 何が起きたか | `elementFromPoint` | `elementsFromPoint` | 矩形が点を含むか |
|---|---|---|---|
| 不透明なオブジェクトの裏に回った | 前面の要素 | 列に入る | 入る |
| 祖先の `overflow:hidden` に切り取られた | 別の要素 | **入らない** | **入る** |
| `pointer-events:none` が乗っている | 別の要素 | **入らない** | **入る** |

見出しは (706, 162)–(1214, 258) にあってポインタは**その中心**に立っているのに、
`elementsFromPoint` が返す 6 要素のどこにも居ない。
**CSS の切り取りは、描画だけでなくヒット判定からも要素を外す。**
選択枠だけは `getBoundingClientRect` を読んで正しく描かれ続けるので、
「枠は見えているのにクリックが通らない」状態になっていた。

**どう決着したか** — 4 つを 1 本のブランチで積んだ。仕様の正は
[features/editing-engine/design.md](features/editing-engine/design.md)、判断は
[同 decisions.md](features/editing-engine/decisions.md) #102〜#105。

1. **そもそも見失わせない** — 移動は要素の 24px が「見える範囲」（スライド ∩ 祖先の `overflow`）に
   残る位置で止める。スライドルート自身も含むので、**スライドの外へのドラッグも同じ規則で塞がった**。
   すでに外に出ている要素は、この規則が現在位置から測るので**最初の 1px で戻ってくる**
   （実測: 重なり −139px → 24px）
2. **Alt+クリック** — 同じ点にある要素の列を 1 歩ずつ奥へ。押した瞬間ではなく**離した瞬間**に
   潜るかどうかを決めるので、Alt ドラッグの複製は一切変えていない
3. **右クリックの「この位置にあるもの」** — 同じ列を一覧で見せ、名前で選ばせる。
   項目を指すとパンくずと同じ破線の枠で示す
4. **選択枠の四辺の掴みしろ** — 拾った要素をドラッグで動かす入口。リサイズハンドルと同じ
   ホスト側の chrome なので、下の要素が切り取られていても届く

**残っているもの** — 1 は矢印キーとリサイズには掛けていない（どちらも 1 回のジェスチャで
全部を外へ追い出すことがない）。覆われた要素と `pointer-events:none` の要素は 2〜4 で拾う。

### #89 WKWebView では編集中の ⌘Z がネイティブ undo に勝てない

**何が起きていたか** — テキスト編集中の ⌘Z が `contenteditable` のネイティブ undo に食われ、
**アプリの履歴は動かないまま DOM だけが戻る**。[#79](#i79) で入れた横取りは Chromium でしか効かない。
ステージのフレームはスクリプトを走らせないので、
**WebKit はホストが張った `keydown` リスナを発火させない**（[ADR-0002](adr/0002-edit-preview-separation.md)）。
[#2](#i2) / [#12](#i12) と同じ壁で、[editing-engine/design.md](features/editing-engine/design.md) の
「インライン編集の抜け方」が既知の壁として持っている。

**実機で計測した**（2026-08-25）。フレームの document に `keydown` / `input` / `pointerdown` /
`paste` / `dragstart` / `focusin` を capture で並べて張り、実ウィンドウで編集して打鍵・⌘Z を送った結果は
**「反応なし」** —— **1 種類も発火しない**。文字は打てているのでフレームはキーを受け取っており、
**ホストから張ったリスナだけが呼ばれない**。同時にツールバーの「元に戻す」は**グレーのまま**で、
アプリの履歴が 1 手も動いていないことも確認した。
つまり壁は推測ではなく実測で、[#79](#i79) の横取りは実機では走っていない。
（計測コードはコミットしていない）

**どう決着したか** — **許容**（2026-08-26）。キーの側から手が出ないことは実測で確定していて、
残る筋は**変異の側**だけ（MutationObserver は境界を越える。貼り付けの洗浄がそれに依存している）。
ただしそこから履歴と辻褄を合わせるには
「ネイティブ undo が戻した状態を新しい 1 手として積む」のか
「アプリ側の履歴に合わせて DOM を引き戻す」のかという**設計判断**が要り、編集エンジンの根に触る。
**担保は「取り返しのつかない状態にしない」ところまで**と決め、その先には踏み込まない。

いま効いているのは、変異が落ち着いた `rAF` で uid を持たない要素があれば `reindex` を回す保険
——**uid を失った要素は残らない**（要素は uid で指す約束は守られる）。
**履歴と DOM のずれは残ったまま**で、⌘Z を押せば文字は戻るので**壊れていることに気づけない**。
ずれが見えるのは、そのあとツールバーの「元に戻す」を押して
**画面に出ているものとは別の markup が現れた**とき。
